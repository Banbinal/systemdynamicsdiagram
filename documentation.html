1. General Syntax

  • Comments: Lines starting with # are treated as comments and ignored by the parser.
  • Whitespace: Whitespace (spaces, tabs) is generally ignored, except for separating keywords, names, and values. Blank lines are also ignored.
  • Case Sensitivity: Keywords (like stock, flow, param) are case-insensitive, but variable names (Population, BirthRate) are case-sensitive. It's recommended to use consistent casing for clarity.
  • Order: While the order of definitions (stocks, flows, etc.) doesn't strictly matter for parsing, it's good practice to group similar elements together for readability. sim and abtest definitions are typically placed at the end.

2. Model Title

You can optionally specify a title for your model, which will be displayed in the UI.

Syntax:
title <Your Model Title>
Example:
title Simple Population Model

3. Model Elements

These define the core components of the system dynamics model.

3.1. Stocks

Stocks represent accumulations or levels within the system.

Syntax:
stock <VariableName> = <InitialValue>
<VariableName>: A unique name for the stock (starting with a letter or underscore, followed by letters, numbers, or underscores).
<InitialValue>: The numeric starting value of the stock at the beginning of the simulation.
Example:
stock Population = 1000
stock Resources = 5000

3.2. Parameters

Parameters are constant values used within the model's equations.

Syntax:
param <VariableName> = <Value>
<VariableName>: A unique name for the parameter.
<Value>: The numeric constant value of the parameter.
Example:
param BirthRate = 0.05
param CarryingCapacity = 10000

3.3. Auxiliaries

Auxiliary variables (or converters) represent intermediate calculations based on other variables. They help break down complex equations.

Syntax:
aux <VariableName> = <Equation> [OptionalPolarityOverrides]
<VariableName>: A unique name for the auxiliary variable.
<Equation>: The mathematical expression defining the auxiliary. See Section 6 for equation syntax.
[OptionalPolarityOverrides]: See Section 6.4.
Example:
aux EffectOfCrowding = (CarryingCapacity - Population) / CarryingCapacity
aux WorkforceGap = TargetWorkforce - Workforce [TargetWorkforce +, Workforce -]

3.4. Flows

Flows represent the rates at which stocks change over time.

Syntax:
flow <VariableName> = <Equation> [OptionalPolarityOverrides]
<VariableName>: A unique name for the flow.
<Equation>: The mathematical expression defining the rate of flow. See Section 6 for equation syntax.
[OptionalPolarityOverrides]: See Section 6.4.
Example:
flow Births = Population * BirthRate * EffectOfCrowding
flow Deaths = Population / AvgLifespan
flow HiringRate = DesiredHiring [DesiredHiring +]

3.5. Graphical Functions

Graphical functions define non-linear relationships using lookup tables (pairs of X, Y points). The tool linearly interpolates between these points.

Syntax:
graph <FunctionName> ( (<x1>, <y1>), (<x2>, <y2>), ... )
<FunctionName>: A unique name for the graphical function.
(<xN>, <yN>): Pairs of numeric X and Y coordinates defining the function. X-values must be strictly increasing. At least two points are required.
Usage in Equations: Call the function like a regular function: <FunctionName>(<InputValue>).
Example:
graph ProductivityEffect ( (0, 0.5), (50, 0.9), (100, 1.0), (150, 0.95), (200, 0.9) )
# Usage in another variable:
aux ActualProductivity = BaseProductivity * ProductivityEffect(Workforce)

4. Connections

Connections define how flows affect stocks.

Inflow Syntax:
connect <FlowName> -> <StockName>
The flow adds to the stock
Outflow Syntax:
connect <FlowName> <- <StockName>
The flow subtracts from the stock
Example:
connect Births -> Population
connect Deaths <- Population
connect ResourceDepletion <- Resources
💡
Remember:

Connections define the relationship between flows and stocks. Make sure every flow is connected to at least one stock to have a complete model.

5. Simulation Settings

Defines the time parameters for the simulation run.

Syntax:
sim <StartTime> <EndTime> <TimeStep>
<StartTime>: The starting time of the simulation (usually 0).
<EndTime>: The ending time of the simulation. Must be greater than StartTime.
<TimeStep> (dt): The time interval for each calculation step in the simulation. Must be positive. Smaller values increase accuracy but take longer to compute.
Example:
sim 0 50 0.5
✓
Best Practice:

For most models, a time step between 0.1 and 1.0 provides a good balance between accuracy and performance. Complex models with rapid changes may require smaller steps.

6. Equations

Equations define the calculations for auxiliaries and flows.

6.1. Syntax

  • Use standard mathematical operators: +, -, *, /, ^ (or ** for exponentiation).
  • Use parentheses () for grouping.
  • Refer to stocks, parameters, auxiliaries, and graphical functions by their defined names.
Examples:
Population * BirthRate
Simple multiplication
(Population / CarryingCapacity) ^ 2
Grouping with exponentiation
100 * (1 - Workforce/MaxWorkforce)
Constant with expression
Population * (BirthRate - DeathRate)
Multiple variables

6.2. Built-in Functions

The parser recognizes specific system dynamics functions:

Function Description Example
STEP(height, stepTime) Returns 0 before stepTime, height at or after stepTime. STEP(10, 5)
PULSE(magnitude, startTime, width) Simulates a pulse starting at startTime with a given magnitude distributed over width. If width is 0 or omitted, the pulse occurs over one dt. PULSE(100, 10, 2)
SMOOTH(input, delayTime) First-order exponential smooth of the input over delayTime. SMOOTH(Demand, 3)
DELAY3(input, delayTime) Third-order exponential delay of the input over delayTime. DELAY3(Orders, 5)

6.3. Math Functions

Standard JavaScript Math functions can be accessed using M. prefix.

Common Math Functions Description Example
M.max(a, b) Returns the larger of the two values M.max(0, Production - Demand)
M.min(a, b) Returns the smaller of the two values M.min(MaxProduction, Demand)
M.sqrt(value) Returns the square root of the value M.sqrt(Area)
M.abs(value) Returns the absolute value M.abs(Error)
M.exp(value) Returns e raised to the power of value M.exp(-Time / TimeConstant)

6.4. Polarity Overrides

For auxiliaries and flows, you can manually specify the polarity of influence from source variables. This helps the tool determine feedback loop types (Reinforcing/Balancing) when the automatic detection is ambiguous (e.g., due to complex equations or graphical functions).

Syntax:
[<SourceVar1> <+/->, <SourceVar2> <+/->, ...]

Added to the end of the aux or flow definition line.

<SourceVarN>: The name of a variable influencing the current aux or flow.
<+/->: Use + if the source variable has a positive influence (increasing the source increases the target) or - if it has a negative influence (increasing the source decreases the target).
Example with Explanations:
# WorkforceGap increases as TargetWorkforce increases (+)
# WorkforceGap decreases as Workforce increases (-)
aux WorkforceGap = TargetWorkforce - Workforce [TargetWorkforce +, Workforce -]

# HiringRate increases as DesiredHiring increases (+)
flow HiringRate = DesiredHiring [DesiredHiring +]
ℹ️
When to use polarity overrides:

Add polarity overrides when the relationship between variables might be ambiguous, especially with complex equations, conditionals (using M.max, M.min), or when using graphical functions. This improves the accuracy of feedback loop identification.

7. A/B Testing

Allows comparing the simulation results for two different values of a single parameter within the same run. Only one abtest definition is allowed per model.

Syntax:
abtest param <ParameterName> = [<ValueA>, <ValueB>]
<ParameterName>: The name of an existing parameter (param) defined in the model.
<ValueA>: The first value to test for the parameter.
<ValueB>: The second value to test for the parameter.
Example:
param AttritionRate = 0.05
# ... other definitions ...
abtest param AttritionRate = [0.05, 0.08]
Common A/B Test Scenarios:
  • Testing different policy options
  • Comparing resource allocation strategies
  • Evaluating sensitivity to key parameters
  • Exploring best/worst case scenarios
A/B Test Limitations:
  • Only one parameter can be tested at a time
  • Only two values (A and B) can be compared
  • The parameter must be defined earlier in the model

8. Full Example

Here's a complete model demonstrating the major DSL features:

# Workforce hiring model (v1.1)
# Demonstrates various DSL features

title Workforce Dynamics with Productivity Effects

# === Stocks ===
stock Workforce = 100

# === Parameters ===
param TargetWorkforce = 150
param AvgTimeToHire = 5      # Average time (e.g., months) to fill a position
param BaseProductivity = 1.0 # Productivity per worker at optimal workforce size
param AttritionRate = 0.05   # Fraction of workforce leaving per time unit

# === Graphical Function ===
# Productivity changes based on workforce size (e.g., due to overhead, training)
graph ProductivityEffect ( (0, 0.5), (50, 0.9), (100, 1.0), (150, 0.95), (200, 0.9) )

# === Auxiliaries ===
# Calculate the gap between target and current workforce
# Explicitly define polarity for clarity
aux WorkforceGap = TargetWorkforce - Workforce [TargetWorkforce +, Workforce -]

# Calculate the desired hiring rate to close the gap over AvgTimeToHire
# Ensure hiring is not negative
aux DesiredHiring = M.max(0, WorkforceGap / AvgTimeToHire) [WorkforceGap +, AvgTimeToHire -]

# Calculate actual productivity per worker using the graph
# Polarity from graph is ambiguous '?', heuristic for BaseProductivity is '+'
aux ActualProductivity = BaseProductivity * ProductivityEffect(Workforce) [BaseProductivity +] # Workforce influence via graph defaults to '?'

# Calculate total production output
aux TotalProduction = Workforce * ActualProductivity [Workforce +, ActualProductivity +]

# === Flows ===
# Hiring rate is based on the desired hiring
flow HiringRate = DesiredHiring [DesiredHiring +]

# Attrition rate depends on current workforce size and rate
flow Attrition = Workforce * AttritionRate [Workforce +, AttritionRate +]

# === Connections ===
# Hiring increases the workforce
connect HiringRate -> Workforce
# Attrition decreases the workforce
connect Attrition <- Workforce

# === Simulation Settings ===
# Simulate from time 0 to 50 with a step of 1 time unit
sim 0 50 1

# === A/B Test Definition ===
# Test the impact of different Attrition Rates
abtest param AttritionRate = [0.05, 0.08]

Understanding this Model

This example models workforce dynamics with feedback loops. It tracks how a workforce changes over time based on hiring and attrition. Key features include:

Balancing Feedback Loop

The model contains a balancing loop where a workforce gap leads to hiring, which increases workforce, which decreases the gap.

Non-Linear Relationship

The graphical function creates a non-linear relationship between workforce size and productivity, with diminishing returns at higher workforce levels.

Explicit Polarities

The model uses polarity overrides to explicitly define the influence direction between variables, ensuring accurate feedback loop analysis.

A/B Testing

The A/B test compares how different attrition rates affect workforce stability and overall production.
